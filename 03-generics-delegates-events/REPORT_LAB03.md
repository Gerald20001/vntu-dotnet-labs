## 1. Мета роботи
Навчитися застосовувати узагальнені (generic) типи та методи, делегати (у т.ч. вбудовані `Func`, `Action`, `Predicate`), лямбда-вирази та механізм подій для побудови гнучкого та повторно використовуваного коду.

---

## 2. Завдання варіанта №1
- **Структура:** Створити власний узагальнений клас `MyStack<T>` з обмеженою місткістю (`capacity`, задається в конструкторі).
- **Обов'язкові операції:**
  - Методи `Push(T item)`, `T Pop()`, `T Peek()`, `bool IsEmpty`, `bool IsFull`, `int Count`.
  - Подія `Overflow` з власним класом аргументів `OverflowEventArgs<T> : EventArgs` (передає відхилений елемент, місткість та час події).
  - Наявність щонайменше 2 підписників на подію `Overflow`:
    1. Класичний іменований метод-логер `LogOverflowToConsole`.
    2. Лямбда-вираз із підрахунком кількості відхилень за сеанс (демонстрація замикань — closures).
  - Узагальнені методи вищого порядку, що приймають стандартні делегати:
    - `FindAll(Predicate<T> match)` — фільтрація елементів;
    - `CountWhere(Func<T, bool> predicate)` — підрахунок елементів за умовою;
    - `ForEach(Action<T> action)` — обхід та виконання дії для кожного елемента;
    - `Select<TResult>(Func<T, TResult> selector)` — трансформація елементів.
  - Демонстрація роботи як на цілих числах `MyStack<int>`, так і на рядках `MyStack<string>`.
- **Граничний випадок:** Виклик `Pop()` або `Peek()` на порожньому стеку — перехоплення винятку `EmptyStackException` без аварійного завершення роботи застосунку.

## 3. Короткий опис реалізації
1. **Узагальненість (`Generics`):** Клас `MyStack<T>` реалізовано незалежно від конкретного типу даних, завдяки чому він однаково коректно працює з `int`, `string` або будь-якими власними класами без пакування (boxing) та втрати продуктивності.
2. **Події та підписники:** Оголошено подію `public event EventHandler<OverflowEventArgs<T>>? Overflow;`. При спробі додати елемент понад `Capacity` метод `Push` викликає `OnOverflow(...)`. На подію одночасно підписано консольний логер та лічильник.
3. **Делегати та лямбди:** Замість створення власних типів делегатів використано стандартні делегати .NET (`Action<T>`, `Func<T, TResult>`, `Predicate<T>`), передані у вигляді лямбда-виразів.

## 4. Порівняння «класичного» методу та лямбда-виразу

### Порівняльний фрагмент коду:
```csharp
// 1. Класичний підхід: окремий іменований метод
public static bool IsEven(int number)
{
    return number % 2 == 0;
}

// Виклик із передачею методу як делегата:
List<int> evenNumbers1 = stack.FindAll(IsEven);


// 2. Сучасний підхід: лямбда-вираз "на місці" (inline)
List<int> evenNumbers2 = stack.FindAll(x => x % 2 == 0);
```

### Пояснення:
- **Іменований метод:** Доречний, коли логіка складна (більше 3–4 рядків), вимагає детального коментування або викликається з багатьох різних місць програми. Проте він засмічує клас дрібними допоміжними методами.
- **Лямбда-вираз:** Забезпечує високу лаконічність і локальність коду — логіка критерію фільтрації знаходиться безпосередньо у місці виклику. Крім того, лямбда-вирази здатні виконувати **замикання (closures)**, тобто захоплювати локальні змінні зовнішнього контексту (наприклад, поріг `threshold`), що неможливо зробити з простим статичним методом без створення додаткового класу-обгортки.

## 5. Лістинги коду

### 5.1. Клас стека (`Collections/MyStack.cs`)
```csharp
using System;
using System.Collections.Generic;
using GenericsDelegatesEvents.Events;
using GenericsDelegatesEvents.Exceptions;

namespace GenericsDelegatesEvents.Collections;

public class MyStack<T>
{
    private readonly List<T> _items;
    public int Capacity { get; }
    public int Count => _items.Count;
    public bool IsEmpty => _items.Count == 0;
    public bool IsFull => _items.Count >= Capacity;

    public event EventHandler<OverflowEventArgs<T>>? Overflow;

    public MyStack(int capacity)
    {
        if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity));
        Capacity = capacity;
        _items = new List<T>(capacity);
    }

    public bool Push(T item)
    {
        if (IsFull)
        {
            Overflow?.Invoke(this, new OverflowEventArgs<T>(item, Capacity));
            return false;
        }
        _items.Add(item);
        return true;
    }

    public T Pop()
    {
        if (IsEmpty) throw new EmptyStackException("Неможливо виконати Pop: стек порожній.");
        int lastIndex = _items.Count - 1;
        T item = _items[lastIndex];
        _items.RemoveAt(lastIndex);
        return item;
    }

    public T Peek()
    {
        if (IsEmpty) throw new EmptyStackException("Неможливо виконати Peek: стек порожній.");
        return _items[^1];
    }

    public List<T> FindAll(Predicate<T> match)
    {
        var result = new List<T>();
        for (int i = _items.Count - 1; i >= 0; i--)
            if (match(_items[i])) result.Add(_items[i]);
        return result;
    }

    public int CountWhere(Func<T, bool> predicate)
    {
        int count = 0;
        foreach (T item in _items) if (predicate(item)) count++;
        return count;
    }

    public void ForEach(Action<T> action)
    {
        for (int i = _items.Count - 1; i >= 0; i--) action(_items[i]);
    }
}
```

## 8. Відповіді на контрольні питання

**1. Навіщо потрібні обмеження типу-параметра (`where T : ...`) в узагальнених класах?**  
*Відповідь:* За замовчуванням компілятор вважає `T` типом `System.Object`, що дозволяє викликати лише методи `ToString()`, `Equals()` тощо. Обмеження (наприклад, `where T : class`, `where T : IComparable<T>`, `where T : new()`) дозволяють гарантувати наявність специфічних інтерфейсів, конструкторів без параметрів чи посилальної природи, відкриваючи доступ до їхніх членів без явного кастингу.

**2. Чим подія (`event`) відрізняється від звичайного публічного делегата-поля?**  
*Відповідь:* Звичайне публічне поле-делегат зовнішній код може як викликати напряму (`delegateField()`), так і випадково перезаписати чи обнулити (`delegateField = null;`). Ключове слово `event` створює захисну інкапсуляцію: зовнішній код може лише підписуватися (`+=`) або відписуватися (`-=`), а сам виклик (`Invoke`) може здійснювати виключно клас-видавець події.

**3. У чому суть замикання (closure) у лямбда-виразі? Наведіть приклад ризику при захопленні змінної циклу.**  
*Відповідь:* Замикання дозволяє лямбда-виразу захоплювати змінні із зовнішньої області видимості. Компілятор створює невидимий допоміжний клас, зберігаючи ці змінні як поля. Ризик у старих версіях C# (до C# 5.0 у `for`) полягав у тому, що лямбда захоплювала посилання на саму змінну лічильника циклу, а не її поточне значення; при наступному виконанні всі лямбди бачили лише фінальне значення змінної.

**4. Чим відрізняються делегати `Func`, `Action` та `Predicate`?**  
*Відповідь:*
- `Action<...>` приймає від 0 до 16 параметрів і нічого не повертає (`void`).
- `Func<..., TResult>` приймає від 0 до 16 вхідних параметрів і обов'язково повертає результат `TResult`.
- `Predicate<T>` — спеціалізований делегат, що приймає один параметр `T` і повертає `bool` (еквівалент `Func<T, bool>`), оптимізований для умов пошуку та валідації.

**5. Які переваги дає використання generics порівняно з типом `object` для узагальненого коду?**  
*Відповідь:*
1. **Типобезпека на етапі компіляції:** неможливо випадково покласти рядок у числовий стек.
2. **Продуктивність:** відсутність операцій боксингу/анбоксингу (boxing/unboxing) для значеннєвих типів (`int`, `double`, `struct`).
3. **Чистота коду:** відсутність необхідності явного приведення типів (`(int)obj`) при отриманні елементів.
